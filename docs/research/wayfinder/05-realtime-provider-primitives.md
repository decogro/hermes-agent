# Wayfinder 05: Realtime provider primitives

**Status:** researched 2026-08-24
**Issue:** [hermes-agent#5](https://github.com/decogro/hermes-agent/issues/5)
**Scope:** Qwen Audio Realtime, Gemini Live, xAI Voice, and OpenAI Realtime adapters.
**Conclusion:** Qwen remains a viable first adapter, but Hermes must own the portable semantics for playback acknowledgement, durable transcript reconciliation, Work receipts, announcement policy, and recovery. xAI has the strongest native pushed-utterance primitive. OpenAI has the clearest native output truncation and provider-managed playback buffer on WebRTC/SIP. Gemini has the strongest documented session resumption and compression story, but asynchronous tool behavior is model-specific.

## Evidence rules

This report uses only official provider documentation and first-party provider source code. “Verified” means the cited provider source explicitly documents the behavior or event. “Inference” means an adapter or Hermes design consequence derived from verified primitives. “Not documented” means the behavior was not established in the reviewed official references, not proof that the provider can never support it.

The local design boundary is fixed by [`CONTEXT.md`](../../../CONTEXT.md), the [Hermes voice ADR](../../adr/0001-hermes-hosts-realtime-voice.md), the [grilling ledger](../../design/grilling-decision-ledger.md), and the [long-session architecture](../realtime-voice-long-session-architecture.md): Hermes owns the durable Voice Conversation, canonical transcript, Work Ledger, provider lifecycle, playback ownership, and pushed Announcement policy. A provider owns native speech inference only.

Capability labels used below:

| Label | Meaning |
| --- | --- |
| **N** | Native provider primitive or event is documented. |
| **M** | Native, but model or transport dependent. |
| **A** | Achievable by Hermes adapter composition, not a provider semantic guarantee. |
| **U** | Not documented in the reviewed official references. |

## Provider semantics

### Qwen Audio Realtime

The verified WebSocket turn is:

```text
input_audio_buffer.append
  -> input_audio_buffer.speech_started
  -> conversation.item.input_audio_transcription.delta*
  -> input_audio_buffer.speech_stopped
  -> input_audio_buffer.committed / conversation.item.created
  -> response.created / response.audio_transcript.delta* / response.audio.delta*
  -> response.audio.done / response.audio_transcript.done
  -> response.done
```

The input transcription event is not just a simple delta: `text` is finalized text and `stash` is tentative text. `response.audio.done` contains no audio bytes. On barge-in, Qwen returns `response.done` with `status=cancelled` and `status_details.reason=turn_detected`; in push-to-talk, the client uses `response.cancel` and receives `client_cancelled`. These facts make Qwen suitable for a normalized `input_started`, `input_partial`, `input_final`, `output_audio`, `output_transcript`, and `response_interrupted` adapter stream.

Qwen's `conversation.item.create` is useful for history projection and function results, but it does not make that history durable. The native context is bounded and earlier history is automatically discarded after the documented turn or audio limits. The adapter must therefore send a compact Hermes checkpoint after every reconnect and treat Qwen context as a cache.

Qwen's function protocol is synchronous at the protocol seam: after `response.function_call_arguments.done`, the client executes the function, inserts `function_call_output`, and sends `response.create`. Hermes can send a short accepted Work receipt immediately, then let the Work Ledger and Announcement path carry the actual result. That receipt behavior is Hermes inference, not a Qwen-native asynchronous function mode.

The QwenAudio first-party agent is useful evidence for adapter glue. Its provider wrapper restores recent conversation with `conversation.item.create` and injects results before `response.create`; its web client tracks scheduled playback and sends playback lifecycle events. Those files are first-party application code, not Qwen service protocol events: [realtime-provider.mjs](https://github.com/QwenAudio/qwen-audio-agent/blob/main/server/src/voice/realtime-provider.mjs), [DashScope adapter](https://github.com/QwenAudio/qwen-audio-agent/blob/main/server/src/voice/providers/dashscope.mjs), and [playback lifecycle](https://github.com/QwenAudio/qwen-audio-agent/blob/main/web/src/playback-lifecycle.js).

### Gemini Live

Gemini's server content can carry model audio, input transcription, output transcription, `generationComplete`, `turnComplete`, and `interrupted`. The API explicitly says input and output transcription are delivered independently with no guaranteed ordering, including no guarantee between output transcription and `serverContent`. The normalized adapter must therefore use provider item and response IDs plus sequence numbers, not arrival order, when reconciling transcript hypotheses.

Automatic VAD is native and interruption is strong: Gemini cancels and discards ongoing generation, retains only information already sent to the client, emits `interrupted`, and cancels pending function calls. The client still has to stop and clear its playback queue. There is no documented provider event that says which milliseconds were physically heard.

History injection is model-specific. Gemini 3.1 permits `clientContent` only for initial history when `initial_history_in_client_content` is enabled; after the first model turn, later text should use `realtimeInput`. Gemini 2.5 permits `clientContent` throughout. This is enough for an adapter, but the adapter must select the model-specific path and never confuse provider history with the Hermes transcript.

Asynchronous function calling is the main portability gap. Gemini 2.5 supports `NON_BLOCKING` and scheduling modes; Gemini 3.1 is sequential and waits for the tool response. A portable Hermes contract must not depend on Gemini 2.5's model-specific behavior. `proactive_audio` is also not a general pushed Announcement primitive: it lets the model decide whether to respond to input.

Gemini is the strongest documented option for long-session provider resumption. The connection lasts around ten minutes, `GoAway` precedes termination, resumption handles are refreshed in `sessionResumptionUpdate`, handles remain valid for two hours after termination, and context window compression can extend session duration. Hermes still remains authoritative because provider resumption can be unavailable, expire, or replay provider-visible context that differs from the canonical transcript.

### xAI Voice

xAI uses an OpenAI-compatible event family but has important semantic differences. Input transcription is `conversation.item.input_audio_transcription.updated`, cumulative and correctable, rather than an incremental delta. Direct WebSocket audio can be JSON/base64 or binary; input and output formats and sample rates are configurable. The direct WebSocket output stream has no provider-managed playback buffer events.

The xAI-specific `force_message` is the closest native match to Hermes pushed Announcements. It speaks exact text through TTS without model inference or `response.create`, emits a normal response lifecycle, and has an `interruptible` policy. It still does not update the Hermes durable transcript or acknowledge physical playback, so Hermes must record the Announcement and wait for a client playback acknowledgement before marking delivery complete.

xAI's opt-in resumption caches user and assistant transcripts, tool calls, and function outputs under a `conversation_id`, replays them on reconnect, and expires after 30 minutes of inactivity. That is useful recovery assistance, not a replacement for Hermes checkpoints. xAI also supports native assistant output truncation through `conversation.item.truncate` and confirms it with `conversation.item.truncated`; the adapter must calculate the duration from local playback for direct WebSocket use.

xAI documents a concrete overlap hazard: function-call events can arrive after all audio deltas, so sending the function result and `response.create` immediately can make the next response overlap audio still playing locally. The required wait for playback completion is direct evidence that `response.done` and output deltas are generation milestones, not playback milestones.

### OpenAI Realtime

OpenAI's current GA event names are `response.output_audio.delta`, `response.output_audio.done`, `response.output_audio_transcript.delta`, and `response.output_audio_transcript.done`. With WebSocket, the server can generate audio faster than real time and the client owns buffering and playback. With WebRTC/SIP, the provider owns an output buffer and emits `output_audio_buffer.started`, `output_audio_buffer.stopped`, and `output_audio_buffer.cleared`.

OpenAI has the clearest native interruption and transcript repair protocol. On WebSocket, VAD speech start cancels the response; the client stops local playback, measures how much audio was actually played, and sends `conversation.item.truncate` with that duration. The server returns `conversation.item.truncated` and removes the unheard transcript. On WebRTC/SIP, the server can automatically truncate its managed output buffer. The client still needs a Hermes playback acknowledgement because provider output-buffer state is not the same thing as the user device's confirmed speaker playback in every topology.

`conversation.item.create` can populate history and insert function results, and the Realtime function protocol is otherwise sequential: receive completed arguments, execute the function, insert `function_call_output`, and send `response.create`. The reviewed Realtime docs do not describe a provider-native long-running Work receipt or a dedicated scripted Announcement event. OpenAI's out-of-band Response facility and ordinary item injection are adapter mechanisms, so Hermes should queue them according to Announcement priority and silence policy.

The reviewed lifecycle guide documents a maximum 60-minute session but no Realtime resumption handle. The safe adapter behavior is to establish a new session, seed it from Hermes's canonical checkpoint, and treat any provider-side conversation state as an optimization only.

## Portable minimum for Hermes

The adapter contract should require these semantics even when a provider does not provide them natively:

1. **Media:** expose the actual input and output codec, sample rate, transport, and whether audio is provider-buffered or client-buffered.
2. **Turn events:** normalize speech start, speech stop, committed input, partial input transcript, final input transcript, response start, output audio, output transcript, generation done, interruption, and connection lifecycle. Preserve provider IDs and event sequence; never assume transcript arrival order.
3. **Barge-in:** stop local playback immediately, emit an interruption distinct from Work cancellation, and retain only audio confirmed as played. A spoken interruption does not cancel an accepted Work unless the user explicitly cancels it.
4. **History:** seed provider context from a Hermes checkpoint with a no-generation operation where available. Provider replay, compression, and native history limits are caches and optimizations, not the durable transcript.
5. **Work:** on `spawn_work`, commit the exact request and Work ID to Hermes and return a short accepted receipt through the active session. The later Work Event becomes a Gateway Announcement. Provider function-call completion must never be the only durable receipt.
6. **Announcements:** accept `push_announcement(text, priority, interruptibility)` from the Gateway. Use xAI `force_message` when available; otherwise compose provider history injection and response creation behind the Gateway's pending-announcement queue. Do not mark delivery at provider generation completion. Require `playback_started`, `playback_finished`, or `playback_cancelled` from the actual audio owner.
7. **Recovery:** reconnect with a new provider session on any close or expiry, optionally using a provider handle, then replay only the required Hermes checkpoint and unresolved Work or Announcement state. Deduplicate by Work ID, Announcement ID, provider session ID, and client playback receipt.
8. **Truncation:** expose `truncate_output(response_id, played_audio_ms)` where native support exists. If it does not, discard the provider's unfinished output and keep Hermes's played-prefix transcript as authority.

The smallest provider-neutral acceptance test is: stream a direct reply before generation completes; interrupt it; verify only played speech is committed; spawn Work and hear an immediate accepted receipt; force a reconnect; inject a pushed completion; interrupt that Announcement according to priority; and verify no duplicate Work or Announcement after replay. Run it once with provider resumption/compression enabled and once with those features disabled.

## Decision

Implement the first adapter against Qwen's documented WebSocket event contract, while keeping provider-specific behavior behind the portable minimum above. Do not make Qwen native history, response cancellation, or `response.done` stand in for Hermes durability or playback synchronization.

Keep xAI as the leading alternative when native pushed announcements are the deciding requirement. Keep OpenAI as the leading alternative when played-audio truncation and direct WebRTC output-buffer control are the deciding requirements. Keep Gemini as the leading alternative when session resumption and compression matter more than one uniform async Work protocol.

These recommendations are architecture inferences from the cited primitives, not provider guarantees or benchmark results.
